\section{The System}

A codebase records what the software does, but it says very little about what each part of it is for or why it was built a particular way.
That knowledge usually lives somewhere outside the code, in a comment, a commit message, a design document that slowly falls behind, or a summary an assistant writes at the end of a working session, and in every one of those places it drifts away from the code as soon as the code moves on.
CoDoc is an attempt to keep that knowledge in one place and hold it current as the code changes.
It maintains a document that describes a codebase in terms of the features it provides and what each feature is responsible for, and it keeps that document and the code synchronized as either side changes.

This section walks through the document itself, the way it is kept faithful to the code, the way a person turns a change in the document into a change in the code, and what the system does when the two disagree.
We introduce each choice through a single running task, shown as it looks in the tool in \autoref{fig:overview} through \autoref{fig:handoff}.
An engineer named Alicia maintains \texttt{tally}, a small command-line tool that turns exported bank statements into spending summaries.
The rules that put transactions into categories are hard-coded, and she wants them moved into a plain file she can edit, along with a weekly summary beside the existing monthly one.
Where it matters, we also point out how an earlier version of CoDoc made a different choice and what that choice cost.
The two directions of synchronization are sketched in \autoref{fig:roundtrip}.

\subsection{The feature document}

Everything in CoDoc is organized around a single document that we call the feature document.
It is a navigable outline of a codebase, written in terms of the features the system provides rather than in terms of the files the code is stored in.
Its unit is a feature, which is a named part of the system together with a short description of what that part is responsible for.
Each feature is linked to the exact code that implements it, and we call those links bindings.
One feature can bind many pieces of code across several files, and any one piece of code belongs to at most one feature, so the document reads as a division of the codebase by purpose rather than as a second copy of the source laid out by file.
The reason for having such a document at all is to give the purpose behind a codebase a place to live where a person can find it, read it, trust it, and change it.

When Alicia opens the repository in Visual Studio Code, the feature document opens as its own editor and she keeps it beside the source, as in \autoref{fig:overview}.
The outline divides \texttt{tally} into concerns such as reading bank statements, money handling policies, and producing spending summaries \mk{1}.
She finds a feature titled Bank export row reader and reads what that part is responsible for \mk{2}.
The names beneath the title are its bindings \mk{3}, and following one lands in \texttt{rows.py} on the exact code, which carries the name of its feature as a label \mk{4}.
Selecting a sentence of the description highlights the bound code beside it, and a small badge reports that the document and the code currently agree \mk{5}.

The important choice here is that the description is something a person writes and reads, while the record of which code implements which feature is a secondary index the system keeps current on its own.
This is where CoDoc differs from the notes teams already keep beside their agents, since a CLAUDE.md file or a memory bank is usually a summary the agent wrote about code that nobody went back to check \citep{agentmemory}, and from recent tools whose live map of a repository is meant for an agent to traverse rather than for a person to sit and read \citep{repograph, speclang}.
CoDoc keeps the live link and hands the description to the person, which follows the argument that automation is most useful when it is arranged around a representation the person still holds \citep{heer2019}.
An earlier version of CoDoc instead mirrored the structure of the code directly, so that a line in the document stood for a file or a function \citep{codoc-prior}.
That made the correspondence easy to see, and it also meant a concern that cut across several files had no natural place to live, which is the main reason we moved to features.
The cost of the newer choice is that the document is only as trustworthy as the effort spent keeping it aligned with the code, so much of the rest of the design is about holding it faithful while asking as little of that effort as possible.

\subsection{Keeping the document faithful to the code}

The first half of the system watches the code and updates the document to match it.
Its aim is to absorb the ordinary churn of day-to-day coding on its own and to ask for a decision only where one is genuinely needed.
CoDoc settles most changes by comparing a fresh reading of the repository against the links it already holds.
When a linked piece of code is edited in place it refreshes the link, when the piece is deleted it drops the link, and when the piece moves to another file or is renamed it follows the code and reattaches the same feature.
The record of which code belongs to which feature therefore survives ordinary refactoring without anyone stepping in.

The cases this bookkeeping cannot settle are code whose behavior no longer matches its description and new code that no feature yet claims.
For those, CoDoc makes a single call to a language model that sees the changed code together with the whole outline and every feature title at once, so it attaches new code to the feature that already owns that purpose instead of inventing a second feature that would mean the same thing.
\autoref{fig:sync} shows the moment this pass completes after the agent's build later in the session.
The terminal reports that the build is in, that the tests pass, and that the descriptions of the touched features were brought back in line \mk{6}.
The description of the period summary has been rewritten to match the code, and the rewrite sits in the document as a tracked change with the old wording struck through beside the new \mk{7}.
Each rewrite names its origin and offers to keep the new wording or restore hers \mk{8}, a bar at the top settles all of them at once \mk{9}, and the one change that would alter the shape of the outline waits separately as a proposal she can accept or reject \mk{10}.

The choice is to read the code as it actually is and let a model judge where it belongs, and to accept that this judgment is approximate and must remain reviewable.
Literate programming and the round-trip tools that followed it instead held prose and code in one form from which either could be regenerated, and both became fragile as soon as real code stopped fitting the grammar \citep{knuth1984}.
CoDoc gives up exact reversibility on the assumption that everyday code is regular enough for a model to attribute correctly most of the time, and that where it is unsure it should raise a proposal rather than decide quietly.
The cost is that this half of the system is not guaranteed to be correct, which is why a change to the document's shape is a proposal a person approves and why review is built in from the start.

\subsection{Turning a description into code}

The second half of the system runs in the other direction and turns a change in the document into a change in the code.
Its central decision is a careful one.
Editing the document counts as documentation by default, and a change becomes a request to change code only through an explicit gesture we call a hand-off.
A description Alicia rewrites is recorded as a held draft that says what is wanted and then waits, and nothing runs, no code changes, and no model is called until she hands it off.

In the session shown, Alicia asks for her change where she already works, in the coding session open in the same window \mk{11}.
The agent reads the code through the same map she reads, and the feature it is currently examining says so \mk{12}.
Rather than editing code straight away, it sketches the plan into the document, where the weekly summary appears as a planned feature in the place it would occupy in the outline \mk{13}.
A planned feature is grey and italic because it describes code that does not exist yet, and the row beneath it states plainly that accepting will ask the agent to write it and that her code will change \mk{14}.
She can reject any piece and accept the rest, one at a time or all at once \mk{15}, and that acceptance is the hand-off.
The agent then carries out the change in her session and returns an ordinary diff, and the revised descriptions come back through the first half of the system as the tracked changes of \autoref{fig:sync}.

Two decisions here are worth stating plainly.
The first is that the hand-off is a deliberate gesture rather than something the system guesses from phrasing.
An earlier version of CoDoc acted on descriptions that sounded like commands, and we removed that because guessing goes wrong in both directions, treating a description that begins with a verb as an order and overlooking a genuine request written as a calm statement.
The second is that the code is written inside the person's own coding session rather than in a separate automated one, so the same run that writes the code also records which feature the new code belongs to, and the document stays plain, editable text.
Systems that made the specification the primary artifact generated code from a structured model edited in place, and the price was that ordinary typing and version control no longer applied \citep{simonyi2006, voelter2011}.
The earlier CoDoc also created placeholder code the moment the document was edited \citep{codoc-prior}, which felt immediate and meant the code began moving before the person had decided they were ready.
The current design waits for the hand-off, and the delay it accepts buys a document a person can write in freely.

\subsection{When the document and the code disagree}

Sooner or later both halves reach for the same feature at once.
Alicia can be partway through rewriting a description at the moment the code side, having noticed a change in the code, wants to update that same feature.
CoDoc settles this with a single rule.
The document wins.
A collaborative editor would let the last writer win or merge the two texts, and one could argue the code side should win because the code is what runs \citep{crdt}.
We chose the document because it is where a person writes down the purpose of the code, while the code side only reports what the code currently does, and a report that had to wait will still be true on the next pass.

In practice, a feature that carries an unresolved edit of hers is held, and the code side may not touch its wording or structure, so a thought she is in the middle of writing is never rewritten under her.
The one thing the hold does not stop is the upkeep of the links, because a link records where code lives and says nothing about what the feature means, so it stays safe to refresh.
The cost is that a held feature can fall briefly behind in detail until she resolves the edit, and we accept that because the alternative is a person losing a half-finished thought to the machine.
What she keeps in return is that the reason for a change stays recorded in the place the change was made, so the next person to open the feature sees that the summary now comes in weeks as well as months and can also see why.
