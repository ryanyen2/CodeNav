Part 1 — User-level overview

What is codoc?

codoc is a persistent, navigable feature tree that sits alongside your codebase. Each node is a named unit of intent — a feature — with a short prose description and links to the code chunks that implement it. The tree is yours: you author it, refine it, and rename it however you like. codoc's job is to keep the links from intent to code accurate as the code changes.

Unlike code-search or auto-documentation tools, codoc doesn't derive the tree from the code on every query. The tree is the ground truth; code attribution is a secondary index that the system maintains incrementally.

One-sentence pitch: codoc is a living table-of-contents for your codebase that never goes stale.

The _index.codoc file

When you run codoc projection render (or hit Cmd+Shift+P → codoc: Open), codoc writes a single file at .codoc/tree/_index.codoc. It's a plain-text indented outline you can read and edit directly in VS Code:

- Checkpoint persistence
    Persists training state so runs can be paused and resumed.

  - Checkpoint file management
      Saves and loads a single checkpoint snapshot to disk.

    - Checkpoint compatibility patching
        Fills in defaults when loading checkpoints from older model versions.

    - Checkpoint discovery
        Finds the latest available checkpoint in a directory.

  - Checkpoint status logging
      Emits a single status message per checkpoint op, suppressing duplicates in distributed runs.

- Dataset file management
    Manages the set of parquet shards that make up the training corpus.

  - Dataset file discovery
      Lists shards already present locally.

Each line that begins with - is a feature. Indentation is 2 spaces per level. The line below the feature title is a one-sentence description. That's the whole file format for stable content.

Day-to-day workflow

1
Open your project in VS Code. Hit Cmd+Shift+P and run codoc: Open. On the very first run it initialises .codoc/, clusters your codebase into features (this may take a minute), and opens _index.codoc.
2
Read and refine the tree. The initial tree is a proposal — every node begins with a + prefix (green diff hunk) meaning "accept me". Rename things, fix intent lines, restructure the hierarchy, and delete features that don't make sense. Just edit the file like any text document.
3
Save. codoc detects the save, parses the file, diffs it against the database, and applies your changes. Accepted features become stable in the DB; any new lines you added become INTRODUCE proposals for your review.
4
Code. As you modify source files, codoc's reflective pipeline observes the changes (on save, or after a git commit) and emits proposals for any features whose code links may need updating.
5
Review proposals. Hunks marked with + - (introduce), - ~ (retire), or ~ - (amend/rename) appear inline in _index.codoc. Accept with the CodeLens button or the bulk status-bar widget; reject to discard.

Proposals: the change-review loop

codoc never changes the feature tree without your approval. Instead it proposes changes as diff hunks inline in _index.codoc:

- Checkpoint persistence
    Persists training state so runs can be paused and resumed.

+ - Checkpoint warm-restart
+     Loads a checkpoint and continues training from the saved step.

- ~ Old checkpoint resume

A + - line is a proposed introduction. A - ~ line is a proposed retirement. A ~ - followed by description lines is a proposed amendment or rename.

You can act on each proposal with the CodeLens buttons that appear above the hunk, or use the status bar widget that shows codoc: 4 pending and lets you accept or reject everything at once.

Feature states

Each feature has a computed state based on how its code bindings look right now:

State Meaning Gutter icon
Stub No code bindings yet (just authored). Purple dot
Drafting Has bindings but some are unresolved. Blue dot
Stable All bindings resolve cleanly. Green dot
Strained Some bindings resolve but others have diverged. Amber dot
Severed All bindings have diverged — the feature's code was moved or deleted. Red dot
Deprecated Feature is intentionally retired. Grey dot

State is computed on every render from live bindings — it is never stored. This means it stays accurate automatically as code evolves.

VS Code experience

Unified entry: A single command codoc: Open auto-detects the repo state and does the right thing — init + bootstrap if no .codoc/ exists, re-render if stale, otherwise just open the file.

Gutter status icons: Every feature line in _index.codoc gets a color-coded dot in the gutter reflecting its current state (green / blue / amber / red / grey). No noisy [State] badge text clutters the prose.

Inline diff styling: Proposed additions glow green, retirements glow red, and amendments glow blue — but the rest of the file stays clean readable prose.

Cross-tab navigation:

  • In _index.codoc, a CodeLens above each feature title reads ▸ bindings. Click it to open a Quick Pick of the bound source files and jump directly to the code.
  • In any .py or .ts source file, a CodeLens above each def/class/function shows the feature it belongs to. Click to navigate back to _index.codoc.

Conflict handling: If you and the server both edit the same feature between syncs, the conflict is annotated inline rather than silently overwritten. A code-action lightbulb lets you choose "use mine", "use server's", or open a three-way diff view.

Part 2 — Architectural deep-dive

User edits Git commits LLM planning │ │ │ ▼ ▼ ▼ Projection sync Reflective pipeline Planning pipeline (parse+diff+apply) (fingerprint+escalate) (diff-hunk proposals) │ │ │ └────────────────────────┴────────────────────────┘ │ ▼ Transaction log (HLC-ordered) SQLite WAL + JSONL audit lane │ ▼ Feature store ←→ Binding index (uuid, slug, title, (feature_uuid → anchors) intent, parent_uuid) │ ▼ Projection render _index.codoc + tree.meta.json
Central thesis — the binding-health loop: for every Binding, the system asks one question: does the stored fingerprint still match current source? The answer is a Comparison with verdict still_aligned | moved | drifted | severed | novel. Every pipeline is either a producer of comparisons (git-diff reflect, on-save reflect, health sweep, bootstrap) or a consumer (apply.py writes new fingerprints on accept; state_derivation reads the latest verdict per feature → FeatureState; the projection renders drift annotations). The lens (_index.codoc ↔ SQLite) is adjacent but contains no drift logic.

Data model

The five core types live in codoc/model/:

TypeKey fieldsNotes
Feature uuid, slug, title, parent_uuid, intent, retired The stable node identity. title is 2–5 words prose; slug is kebab-case. State is derived, never stored.
Anchor file, symbol_path?, ts_query?, occurrence_index Points at a code chunk without byte ranges (those are resolved live by tree-sitter).
Binding uuid, feature_uuid, anchor, fingerprint Links a feature to one code chunk. A feature can have many bindings across many files.
Transaction hlc, kind, payload, author, proposal Append-only log entry. proposal=True means pending user review.
HLC logical_time, wall_clock, node_id Hybrid Logical Clock — lexicographically sortable, causal across nodes.

Transaction log and HLC

Every change to the feature tree goes through the TransactionLog (codoc/core/log.py). There are two write paths:

  • append_proposal(tx) — writes a proposal (pending review). Automatically deduplicates INTRODUCE proposals for the same (slug, parent_uuid) pair.
  • append(tx) — writes an accepted intentional transaction (AMEND, RENAME, RETIRE) directly, bypassing the proposal queue.

Each transaction receives an HLC timestamp stamped at write time. The HLC advances monotonically, incorporates wall-clock time, and is safe across concurrent nodes without coordination. The HLC string is the primary key in SQLite (transactions table).

The JSONL audit lane at .codoc/log.jsonl is a complete rebuild-able copy of the SQLite log — useful for inspection, diffing, and migration.

Tree-alignment identity

The hardest problem in projection sync is feature identity under rename. When you rename a feature in _index.codoc, codoc must recognise that the renamed feature is the same DB record — not retire the old one and introduce a new one (which would destroy history).

codoc solves this with a two-tier resolution algorithm in codoc/projection/parser.py and codoc/projection/tree_align.py:

  1. Sidecar lookup — the tree.meta.json sidecar carries title_path_to_uuid and slug_path_to_uuid maps written at the last render. If either map contains the feature, that UUID wins immediately — O(1), no heuristics.
  2. Structural recovery (last-resort) — when the sidecar misses (first sync after a rename, or after the sidecar is deleted), tree_align.resolve_uuid_structural runs one scoring pass over all siblings under the same parent. Each sibling is scored by max(title_exact, slug_normalised_match, levenshtein_ratio); the best-scoring UUID is returned if the score is ≥ 0.6. If two siblings score equally the match is ambiguous and becomes an INTRODUCE proposal instead of a silent identity assignment.

The sibling index is pre-built in O(N) once per sync cycle as a parent_uuid → [children] map, making the scoring pass O(children).

Features that still fail to match become INTRODUCE proposals rather than fatal errors — you may have genuinely added a new feature, and codoc will ask you to confirm.

Projection layer

The projection layer is the bridge between the _index.codoc text and the SQLite store. It lives in codoc/projection/:

ModuleRole
tree_codoc.pyRender: DB → _index.codoc + tree.meta.json sidecar
parser.pyParse: _index.codoc → ParsedTree (uses tree-align for identity)
differ.pyDiff: ParsedTree × DB → list of IntentOp
sync.pySync: parse + diff + apply + re-render in one transaction
meta.pyTreeMeta sidecar schema + read/write helpers
tree_align.pyStructural identity resolution (see above)

The tree.meta.json sidecar is written alongside _index.codoc on every render. It carries:

  • uuid_to_location — maps each feature UUID to its rendered line number plus structural fields (depth, sibling_index, parent_uuid, title_norm_hash) used by the identity algorithm on the next parse.
  • title_path_to_uuid and slug_path_to_uuid — the primary identity lookups used by Tier 1 resolution (fast, no heuristics).
  • line_range_to_hlc — maps diff-hunk line ranges to proposal HLCs, so the extension can look up the HLC for any line in a proposal hunk without embedding HLC text in the file.
  • feature_hashes — sha1(title + intent + parent_uuid + retired) per feature, used for conflict detection.

Reflective pipeline

When you save a source file (or after a git commit), the reflective pipeline observes the change and proposes binding updates:

On-save / post-commit
       │
       ▼
tree-sitter re-parse      ← tree_walk(source, adapter) → tokens_hash, types_hash, minhash
       │
       ▼
reconciler.compare        ← per binding: stored fingerprint vs current source
       │
  ┌────┴────────────────┐
  │  still_aligned      │   skip — update fingerprint cache
  └─────────────────────┘
       │ not aligned
  ┌────┴────────────────┐
  │  moved              │   types_hash match → MOVED proposal (no LLM)
  └─────────────────────┘
       │ drifted / severed / novel
       ▼
namespace-absorb gate     ← symbol-prefix majority → ABSORB directly
       │ low confidence
       ▼
LLM escalation            ← attribution agent (1–3 s)
       │
       ▼
proposal queue            ← stored as pending transactions in SQLite

The key design: one comparison function (reconciler.compare) drives both the reflective pipeline and the periodic health sweep. The pipeline scales with the change, not the codebase. After bootstrap, it never re-indexes everything. Structurally unchanged chunks are detected without an LLM; only genuine semantic drift escalates.

Sync invariants

The sync path enforces three invariants:

  1. Invariant 1 (identity preserved): A feature whose title changed in _index.codoc must map to the same UUID — not produce a RETIRE+INTRODUCE pair. Enforced by the two-tier sidecar + structural-recovery algorithm.
  2. Invariant 2 (proposals round-trip): A proposal accepted or rejected in _index.codoc (by deleting or editing the diff hunk) must be applied atomically in the DB and the file re-rendered without the hunk. Enforced by the AcceptOp/RejectOp pathway in sync.py.
  3. Invariant 3 (race-safe sync): If the store head HLC has advanced since the last render (another writer, e.g. the reflective pipeline, committed while the user was editing), user changes to untouched features apply cleanly. Changes to the same feature as the server produce an inline <!-- conflict --> annotation rather than silently overwriting.

Extension architecture

The VS Code extension (vscode-codoc/src/) communicates with the codoc FastAPI server over HTTP. The server runs locally; the extension connects to it on port 8001 (configurable).

State layer

  • state/server.ts — manages the server process lifecycle and the CodocClient HTTP wrapper.
  • state/line-tracker.ts — maintains a Map<uuid, {startLine, endLine}> that applies incremental line shifts from onDidChangeTextDocument events. Decorations re-read from this tracker, not from a stale sidecar.
  • state/proposals-status-bar.ts — right-aligned pending-count widget with bulk accept/reject.

Provider layer

  • providers/decoration.ts — gutter status icons + diff-hunk background tints.
  • providers/codelens.ts — sync / render / reflect buttons + per-proposal accept/reject + feature-to-bindings navigation.
  • providers/code-lens.ts — reverse lens on source files (code → feature).
  • providers/code-actions.ts — lightbulb accept/reject on diff-hunk lines.
  • providers/conflict-resolver.ts — virtual document provider for codoc-conflict:// three-way diff URIs.
Echo suppression (Phase 1.5 TODO): The server → render → FS-event → sync → render loop is currently suppressed at the debouncer level (750 ms cooldown after a server-triggered render). A proper render-token echo guard (stamped in tree.meta.json, checked by the extension before dispatching a sync) is deferred to Phase 1.5 when the full FS-watcher lands.
HLC lookup for new-format hunks: Old proposal lines embedded the HLC directly in the text (# ?HLC). New-format diff hunks store only content. The extension resolves an HLC for any line by checking tree.meta.json.line_range_to_hlc — a map from "_index.codoc:start-end" ranges to HLC strings written by the renderer at render time.
