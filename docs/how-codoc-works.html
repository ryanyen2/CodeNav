Part 1 — User-level overview

What is codoc?

codoc is a persistent, navigable feature tree that sits alongside your codebase. Each node is a named unit of intent — a feature — with a prose description and optional inline citations to the code that implements it. The tree is yours: you author it, refine it, and rename it however you like. codoc's job is to keep the links from intent to code accurate as the code changes, in both directions, while humans and AI agents edit both sides concurrently.

Unlike code-search or auto-documentation tools, codoc doesn't derive the tree from code on every query. The tree is first-class authored intent (ground truth); code attribution — the bindings — is a secondary index the system maintains incrementally.

One-sentence pitch: codoc is a living table-of-contents for your codebase that never goes stale — and a two-way bridge where editing the map can drive the code, and editing the code refines the map.

The tree.codoc file

After setup, the one human-facing file lives at .codoc/tree.codoc. It's a plain-text indented outline you can read and edit directly:

- Authentication flow  ⟨f-3a9c2e⟩
    Handles login, session creation, and token lifecycle.

    Cites [session creation](codoc:auth.py#AuthManager.create_session).

  - Token rotation  ⟨f-7b1d04⟩
      Refreshes session tokens before expiry.

  - Password reset  ⟨f-cc90f1⟩
      Lets a user reset a forgotten password via an emailed one-time token.

  ~ Legacy HTTP Basic auth  ⟨f-2c8b01⟩
      Deprecated in v3; removed from all production paths.

- Notification dispatch  ⟨f-1f88aa⟩
    Queues and flushes email + in-app notifications.

Each - line is a live feature. ~ marks a retired feature (struck-through in VS Code). Indentation (2 spaces per level) determines the hierarchy. Descriptions are free prose and may span multiple paragraphs. The hidden ⟨f-…⟩ id is the stable identity that survives renames — the VS Code extension renders it invisible. Inline [label](codoc:file.py#symbol) links are how you cite code; derived bindings are shown as inlay chips, not written into the text.

Three further markdown-native signals live inside descriptions and steer the agent — see § Markdown-native signals: > … blockquote steering comments, **bold** focus, and external [label](https://…) links.

Install & set up

The recommended path is the VS Code extension. Install the codoc extension and run "codoc: Set up codoc" — offered on first run, or via the $(rocket) Set up codoc status-bar item. One click then does everything that used to be manual:

  1. Provisions the Python core into an isolated uv-managed environment (a wheel bundled in the extension; uv itself is fetched if missing). No global pip install, no virtualenv juggling.
  2. Reuses your Claude Code login for codoc's own reflection model — no second API key to paste. (An OpenAI key is the fallback.)
  3. Runs codoc init — indexes the repo, proposes a starting tree, and installs the Claude Code plugin (hooks + MCP + skill + slash commands).
  4. Owns the codoc watch daemon's lifecycle — starts it, keeps a single owner per repo, and stops it when the window closes. You never run watch by hand.

Everything is gated on VS Code Workspace Trust — no process is spawned in an untrusted folder.

Manual / no-IDE path. For scripting or headless use: 
# codoc is not on PyPI — that name belongs to an unrelated project. Install from git:
uv tool install git+https://github.com/ryanyen2/CodeNav.git   # isolated (Python 3.11–3.12)
#   …or from a clone:  git clone … && cd CodeNav && pip install -e .
export CODOC_PROVIDER=claude   # reuse your Claude Code login — no separate key
#   …or OpenAI:  export CODOC_PROVIDER=openai && export OPENAI_API_KEY=sk-…
cd ~/code/my-project && codoc init

Day-to-day workflow

1
Set up once. Click "codoc: Set up codoc" in VS Code (or run codoc init). This indexes the repo (incrementally — a killed run resumes from the last completed file), proposes a hierarchy, and writes .codoc/tree.codoc.
2
Read and refine the tree. Rename things, fix descriptions, restructure the hierarchy — edit the file (or the Codoc Tree view) like any document. The initial tree is a starting point; intent is yours to author.
3
The daemon is already running. The extension keeps codoc watch alive for you. It watches both code files and the .codoc/ control files, reacting to changes in either direction.
4
Code. Modify source files (you, or Claude Code). codoc detects changes, auto-applies safe updates (re-attach a moved symbol, refresh a binding), and places structural proposals in-situ in the tree for review.
5
Edit the tree. Change a description, rename a node, or add one. If the edit requests code (it reads imperative, or it's a plan node), codoc builds a coding directive and queues it for your live Claude Code session in .codoc/realize.md. You run /codoc:sync to implement it.
6
Review proposals. Proposals appear inline at their target position. Click Accept or Reject — no text to type.
codoc never writes code on its own. Implementation runs in your interactive Claude Code session via /codoc:sync, with your normal permissions. (An optional codoc watch --auto-realize exists for unattended fallback, but the default flow always keeps you in the loop.)

Proposals: the in-situ review loop

codoc never changes the feature tree without your approval. Instead it surfaces each change as an in-place overlay — at the exact tree position where the change would land. ADD and MOVE render as ghost hunks; RETIRE and AMEND decorate the live node in place (a strike, or an inline title/description diff):

- Authentication flow  ⟨f-3a9c2e⟩
    Handles login, session creation, and token lifecycle.

+ - Rate limiting  ⟨e-9f01c2⟩
+     Caps API requests per user per minute.

  - Token rotation  ⟨f-7b1d04⟩

A + line (green) is a proposed addition; ~ (blue) a move or amendment; a strike (red) a retirement. The ⟨e-id⟩ identifies the pending event — you never type it. Use the Accept / Reject actions on each proposal, or Accept all / Reject all from the header. Verdicts are written to .codoc/inbox.json; the loop applies them and clears the overlay on the next write cycle. (From the shell you can also codoc accept <e-id> / codoc reject <e-id>.)

Two viewers, one surface. The same proposals render both in the raw-text tree.codoc editor (ghost hunks + CodeLens) and in the Codoc Tree webview (ghost rows / strike / inline description diff with inline ✓/✗). There is no separate "proposals" panel.

Markdown-native signals: steering, focus, links

Three ordinary markdown constructs in a description become instructions to the realizing agent — no special syntax to learn:

SignalMarkdownWhat it does
Steering comment > check the rate-limit headers too A note addressed to the agent, not prose. Loop B drains each into a STEER FEATURE directive (always imperative, appended to an in-flight queue so you can steer mid-generation); the next render consumes it from the text. In the webview you author one by selecting prose → the comment bubble → a composer.
Focus … cap **per user_id** per minute Newly-bolded spans ride into the directive as a Focus: line. A newly-bolded span that itself reads imperative queues a directive even when the description as a whole is descriptive.
Consult link [token bucket](https://…) External https:// links become Consult: lines — the realizing agent WebFetches them before implementing.

Claude Code integration

codoc ships as a Claude Code plugin — hooks, an MCP server, a skill, and slash commands — all installed into the repo by codoc init. There is no server process and no port; everything is file-based.

Two roles for Claude:

RoleHow invokedWhat it does
Planning You ask Claude a question; it loads the codoc-intent skill, or you run /codoc:plan Proposes changes to tree.codoc via the codoc MCP tools (codoc_plan_add / codoc_propose_*). No code is touched yet — the human Accepts in the IDE.
Implementation You run /codoc:sync in your session (nudged by a hook) Reads the directive codoc queued, writes the code, calls codoc_reflect to bind it. Runs in your interactive session, with your permissions — never a headless claude -p.

The MCP server (codoc, registered in .mcp.json as the codoc-mcp console script; FastMCP over stdio) is the agent's primary reflection path. Instead of relying on Loop A's blind index-diff, Claude calls tools that carry real intent straight into the store:

  • codoc_tree / codoc_status — read the current tree + lifecycle state.
  • codoc_propose_add / _amend / _move / _retire — author a structural proposal.
  • codoc_attach — bind code to an existing feature.
  • codoc_reflect — bulk-reconcile after writing code (pass caused_by=⟨d-id⟩ to chain it to the directive it implements).
  • codoc_plan_add — author an unrealized plan node (realized only once code binds).
  • codoc_await_verdicts — block on the IDE inbox so a plan can be proposed, accepted, and implemented in one turn.

The hooks (deep-merged into .claude/settings.json): SessionStart, Stop, PreToolUse (Edit|Write|MultiEdit|Read), PostToolUse (Edit|Write|MultiEdit), and UserPromptSubmit.

  • PreToolUse / PostToolUse write .codoc/activity.json as Claude reads and modifies files — which files, in which mode, and which features they belong to. The extension watches this and shows live activity in the tree.
  • Stop runs a recovery-grade reflection (Loop A) on what the session changed, so the tree stays current even with no daemon running.
  • UserPromptSubmit nudges you to run /codoc:sync when Loop B has queued work (status = awaiting_impl), and drains the inbox as a fallback when no daemon owns the repo.

The hooks never block the agent; they're fire-and-forget with a short timeout.

Single Claude auth. When CODOC_PROVIDER=claude (the extension's default), codoc's own reflection LLM pass shells out to your authenticated claude CLI keyless (prompt delivered over stdin, API-key env scrubbed, run from a neutral cwd). One login powers both the agent you talk to and codoc's internal classification — no separate model account.

VS Code experience

The extension is entirely file-based — no HTTP client, no server, no port. tree.codoc opens in either of two editors:

The Codoc Tree webview (the default editor) is a rich-text view of the tree built on TipTap/ProseMirror, with one editing surface — no modes. Headings are feature nodes; body text is the description. You just edit; what an edit means is decided by the daemon, and changes flow in two asymmetric directions:

  • Your edits commit — and a feature whose edit implies code wears a calm "realizing" badge (the agent is catching up; ✕ to withdraw). A faithful realization clears it; a divergent one is flagged for review. No strike on your own typing. See the collaborative-editing model.
  • Agent changes are tracked changes you review — drift/reflection/amend render as the vendored engine's insertion/deletion marks (struck old / inserted new), tinted per author, with inline ✓/✗. ADD/MOVE keep ghost rows, RETIRE a strike, with toolbar Accept-all / Reject-all.
  • Inline comments — select prose → a comment bubble → a composer. The note anchors to the span and is handed to Loop B as a one-shot STEER directive.
  • Code-ref chips with @-autocomplete from the AST-bound symbols.

The webview persists its authored doc to .codoc/tree.doc.json and never writes tree.codoc — the daemon is the sole writer of that file, which closes the save-conflict the two-writer model used to hit.

The raw-text tree.codoc editor is the plain-markdown alternative, with: hidden ⟨…⟩ ids and colored proposal hunks (decorations); derived-binding inlay chips; per-proposal Accept/Reject CodeLens + lightbulb; clickable codoc: refs that open the target in a split pane; [-triggered ref autocomplete; dependency-focus dimming and a static agent-activity gutter; folding / outline / nav helpers, including ⌘K tree-nav chords.

Status bar. A single item follows .codoc/status.json:

StateStatus bar
realizing$(loading~spin) implementing…
tree_dirty$(pencil) applying tree edits…
awaiting_impl$(play) N to implement
code_drift$(bell) N proposals
in_sync$(check) N
not initialized$(rocket) Set up codoc

Part 2 — Architectural deep-dive

User edits tree.codoc User / agent edits source code │ │ ▼ ▼ Loop B — codoc → code Loop A — code → codoc drain edits.json + inbox.json update_index (cocoindex) parse + diff tree.codoc compute_changeset apply user ops immediately auto-ops (REFRESH/ATTACH/DETACH) drain > … steering comments relocation detection (no LLM) build directives, mint ⟨d-…⟩ one LLM pass for structural ops queue realize.md + realize.json structural ops → pending Events status = awaiting_impl doc-wins holds + caused_by stamping │ │ └──────────────────┬──────────────────┘ ▼ Store (SQLite WAL) features · bindings · events (the ledger) │ ▼ render.py → write_tree tree.codoc + tree.bindings.json (v4) (atomic tmp→rename) │ ▼ live Claude session runs /codoc:sync → implements
Central design: the store (SQLite) is the single source of truth. tree.codoc is a rendered view of it — not a database replica. Loop A and Loop B both write the store; write_tree renders it back to disk. The extension reads the rendered files; no HTTP, no server process.

Data model & the change ledger

Core types live in codoc/model/:

TypeKey fieldsNotes
Feature id, title, description, parent_id, retired, realized, created_at, updated_at Stable identity via id (f-xxxxxxxx). One prose field: description. retired + realized are the only lifecycle bits — realized=False marks an accepted plan node with no code yet; the first binding flips it True.
Binding id, feature_id, file, symbol_path, fingerprint Links a feature to one code chunk. UNIQUE(file, symbol_path) — a chunk binds to at most one feature. fingerprint = tokens_hash for staleness detection.
Event id, at, source, op, applied, accepted_at, actor, mode, caused_by Append-only log entry. applied=False = pending proposal. The last three fields are the change ledger (below).
NodeOp kind, feature_id, parent_id, title, description, bindings, rationale, realized The payload of an Event. Safe kinds: ATTACH DETACH REFRESH AMEND (AMEND auto-applied only when the edit is small — AMEND_SAFE_RATIO). Structural: ADD_NODE MOVE_NODE RETIRE_NODE.
HLC logical_time, wall_clock, node_id Hybrid Logical Clock — lexicographically sortable, causal. Used for created_at/updated_at/at everywhere.

Three authoritative SQLite tables: features, bindings, events. One derived cache: code_edges(src_symbol, dst_symbol, kind, internal) — safe to drop and rebuild from the chunk index. The chunk index itself (AST chunks + embeddings + identity hashes) lives outside codoc.db, in .codoc/lancedb/ (cocoindex + LanceDB).

The change ledger. Every tree mutation is stamped so the IDE can render who changed what, how, and because of which prior change:

FieldValuesMeaning
actorhuman · agent id (claude-code, …) · loopwho made the change
modepen · suggest · autohow it landed: direct authoritative edit / proposed (needs a verdict) / machine-applied safe maintenance
caused_byd-… directive · e-… event · suggestion id · ""the prior change this one implements — the causality chain

One explicit decision table (codoc/loop/classify.py) maps every change — either side, any actor — to one reaction, including the doc-wins conflict policy (a feature with pending doc-ahead intent suppresses code-side AMEND/RETIRE/MOVE; bindings are still maintained, because bindings are attribution, not intent). The full prose counterpart is docs/codoc-change-ledger.md.

Loop A — code → codoc

Triggered whenever source files change. compute_changeset reads the old and new index snapshots from LanceDB, keys by (file, symbol_path), and compares tokens_hash → ChangeSet{added, removed, modified}. Then five phases:

  1. Auto-ops. derive_auto_ops resolves trivially-safe changes (modified-bound → REFRESH, removed-bound → DETACH) with no LLM.
  2. Correspondence. _detect_relocations pairs removed↔added chunks that are the same code relocated: a move (identical tokens_hash) or a rename (same-file unique types_hash). Each match emits a deterministic ATTACH to the prior feature — no LLM, no risk of lost attribution.
  3. LLM pass. Runs only if there are still-unbound additions, a feature lost its last binding, or an in-place modify may have staled a realized feature's prose. ONE propose_tree_update call with the change set, a file-locality seed subtree, and every node title (de-dup context). Safe ops apply immediately; structural ops become applied=False proposal Events.
  4. May-impact. _compute_impacted surfaces upstream dependent features of changed symbols into the prompt (observability).
  5. Coverage net. _cover_uncovered_adds ensures no added chunk is silently dropped — it attaches to the graph-neighbor_feature with the most call/import edges to the new symbol, or surfaces a pending ADD_NODE proposal.

Two authority flags, set by the caller (not the op), gate the destructive ops: run_loop_a (the twitchy temporal index diff) passes allow_retire=False, amend_on_change=False; reconcile_drift (the authoritative full-state pass — the production daemon path) passes both True. So a RETIRE is only ever surfaced from the authoritative state view, never a mid-edit diff. While a realize queue is open, every op the pass applies is stamped caused_by=⟨directive id⟩ so the IDE groups the surfaced-back changes under the doc edit that triggered them. A stale-proposal GC runs first each pass, clearing false-positive ADD/RETIRE proposals once code rebinds — so a no-op codoc sync converges to in_sync.

Loop B — codoc → code

Triggered when the webview commits an edit to .codoc/tree.doc.json, when the raw tree.codoc changes, when inbox.json has new verdicts, or when a comment steer / withdrawal lands in edits.json. In order:

  1. Drain cancellations + annotations, snapshot the diff. Prune any withdrawn directives from the queue; read edits.json authorship annotations; then diff the edit source against the pre-mutation store — preferring tree.doc.json (the webview's authored doc; single-writer) when it carries a pending edit, else the tree.codoc text (raw-editor edits). Diffing after verdicts would read the accepted text as a human edit and revert it.
  2. Drain inbox. For each verdict: accept → apply_op + consume the event; reject → delete it.
  3. Apply user ops. User edits are intentional — applied immediately, stamped with the annotating actor/mode (default human/pen).
  4. Drain steering. Turn each inline-comment steer (from edits.json) and any raw > … comment into a STEER FEATURE directive.
  5. Re-render tree.codoc when the pass mutated the store.
  6. Build & queue directives. For each code-implying op, render a directive (prompts/realize.txt) with Focus: / Consult: lines, mint a d-… id, and write it to .codoc/realize.md + the realize.json manifest. Set status.json = awaiting_impl.

The queue appends instead of clobbering: realize.json carries each directive's rendered text, so a steering comment can land while a realization is in flight. RETIRE is path-asymmetric: accepting an auto-raised retire from the inbox is detach-only (it untracks but never deletes code); only a human ~ retire in the text queues a code-removal directive — deleting code on accept is the most destructive failure mode, so it requires explicit intent.

No headless implementation in the loop. Loop B does not spawn claude -p to write code. It hands the work to your live session by writing realize.md and setting awaiting_impl; you run /codoc:sync. The loop is then closed by the Stop-hook reflection or the watch daemon's Loop A pass.

Realization: the queue & engines

The primary path is in-session: /codoc:plan proposes nodes then calls the blocking codoc_await_verdicts tool — it polls inbox.json, applies each verdict as it lands, and returns so the same turn implements and binds. No daemon, no idle gap. Two fallbacks reuse realize.md for when no session is waiting:

  • The UserPromptSubmit hook drains the inbox via Loop B when no codoc watch daemon owns the repo — so a plan accepted with no daemon still queues work on the next prompt.
  • codoc watch --auto-realize spawns an unattended pass when a queue exists and no interactive session is open — the only path that lands code with nobody at the keyboard. It prefers the Claude Agent SDK engine (loop/sdk_realize.py, when codoc[sdk] is installed) which runs /codoc:sync via query() and streams one compact line per agent action while mirroring activity signals to the IDE; otherwise it falls back to a blind claude -p /codoc:sync.

The unified /codoc:sync command reads status.json and dispatches direction: awaiting_impl/tree_dirty → realize; code_drift → reflect. codoc realize runs the SDK engine in the foreground.

File format and round-trip invariant

The key correctness property: render → parse → diff is always a no-op.

This is enforced by identifying proposal blocks via their ⟨e-id⟩ (event id) vs the ⟨f-id⟩ on live features — both parsers (parse.py and the TypeScript tree-model.ts) skip proposal blocks entirely. The diff step only sees live features, so a round-trip produces zero ops. RETIRE/AMEND emit no text (they ride in the sidecar, decorating the live node in place) — keeping the live node byte-identical to a clean render is what preserves the round-trip.

tree.codoc on disk after a propose_add:

- Authentication flow  ⟨f-3a9c2e⟩
    Handles login, session creation, and token lifecycle.

+ - Rate limiting  ⟨e-9f01c2⟩       ← proposal block (skipped by parser)
+     Caps API requests per user per minute.

  - Token rotation  ⟨f-7b1d04⟩       ← live node (parsed normally)

Both parsers are parity-tested against each other on real trees. Descriptions may span multiple paragraphs — a node ends only at the next feature-marker line, the pending sentinel, or EOF; blank lines are kept.

Sidecar, status & control files

render.py writes two files atomically (tmp → rename) on every write_tree call. The sidecar is pure derived state and is also written independently on every pass — even when the tree.codoc text render is held back to preserve an un-absorbed human edit — so applied verdicts / new bindings / proposal changes surface in the IDE immediately.

tree.bindings.json — the IDE sidecar, schema version 4:

{
  "version": 4,
  "by_feature":   { "f-id": [{"file": "auth.py", "symbol": "auth.py::AuthManager.login"}] },
  "by_file":      { "auth.py": [{"symbol": "...", "feature_id": "f-id", "feature_title": "..."}] },
  "features":     { "f-id": {"title": "...", "parent_id": null, "realized": true} },
  "feature_edges":{ "f-id": [{"to": "f-other", "weight": 4, "kinds": ["call"]}] },
  "proposals":    { "by_feature": { "f-id": {"op": "amend", "event_id": "e-…",
                                             "actor": "...", "mode": "...", "caused_by": "..."} },
                    "by_event":   { "e-id": {"op": "...", "...": "..."} } },
  "changes":      [{"event_id": "e-…", "at": "...", "kind": "AMEND",
                    "feature_id": "f-id", "actor": "...", "mode": "...", "caused_by": "..."}],
  "holds":        ["f-id"]
}
  • proposals.by_feature drives the in-place retire/amend overlays + Accept/Reject on the live node; realized drives the unrealized-placeholder decoration.
  • changes (last ~50 applied events, newest first) drives the agent-pencil re-stamp in the webview.
  • holds is the doc-wins hold set; a non-empty proposal caused_by renders the inline ↳ from your edit cascade cue.

The loops (not write_tree) maintain a small set of JSON / markdown control files in .codoc/:

inbox.jsonIDEverdict channel: Accept/Reject writes here; Loop B drains and clears it.

Plus the data stores: codoc.db (features + bindings + events, SQLite WAL), lancedb/ (incremental chunk index, cocoindex), and — for the rich webview — tree.doc.json (the authoritative ProseMirror doc holding authorship marks + comment threads; tree.codoc is a byte-identical derived projection the Python loops consume).

Extension architecture

The VS Code extension (vscode-codoc/src/) is entirely file-based. WorkspaceState watches **/.codoc/{tree.codoc, tree.bindings.json, status.json, inbox.json}, reparses on change, and fires onDidChange; all providers update synchronously — no polling, no HTTP.

State + setup

  • state/workspace-state.ts — root detection, file watchers, status bar, writeVerdict(), the codoc.ready context key, provisioning state.
  • state/tree-model.ts — TypeScript port of parse.py (parity-tested); harvests proposal hunks + inline refs.
  • state/bindings-model.ts / comment-model.ts / edits-channel.ts / status-presentation.ts — sidecar types, the comment lifecycle, the edits/intents contract, and the pure status-bar view.
  • setup/{provision,credentials,env-file,paths,setup-flow}.ts — uv provisioning, credential bootstrap, the keyless-Claude default, and the one-click orchestration.
  • daemon/{daemon-manager,lockfile}.ts — extension-owned codoc watch: single-owner lockfile, parent-death self-exit, sync SIGTERM on window close.

Editors + providers

  • providers/tree-editor.ts + webview/tiptap/* — the Codoc Tree webview (default editor): inline proposals, author marks, suggestions, code-ref chips, and the inline-comment lifecycle (comment-decorations.ts, comment-mark.ts).
  • providers/decoration.ts — hides ⟨…⟩ ids, colors proposal hunks, strikes retired nodes.
  • providers/inlay.ts — derived-binding chips per title line.
  • providers/codoc-tree-lens.ts / code-actions.ts — per-proposal Accept/Reject CodeLens + lightbulb.
  • providers/code-lens.ts — source-file CodeLens: which feature owns a symbol.
  • providers/{completion,doc-links,focus,agent,file-decoration,folding,symbol,feature-lines}.ts — ref autocomplete, clickable codoc: links, dependency dimming, the agent gutter, Explorer badges, and outline/fold/nav helpers.
Self-write guard: watch.py tracks the last time it wrote tree.codoc and ignores FS events within a short window after its own write, so the daemon never triggers itself in a loop when it re-renders after applying ops.
