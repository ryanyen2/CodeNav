Part 1 — User-level overview

What is codoc?

codoc is a persistent, navigable feature tree that sits alongside your codebase. Each node is a named unit of intent — a feature — with a prose description and optional inline citations to the code that implements it. The tree is yours: you author it, refine it, and rename it however you like. codoc's job is to keep the links from intent to code accurate as the code changes.

Unlike code-search or auto-documentation tools, codoc doesn't derive the tree from code on every query. The tree is ground truth; code attribution is a secondary index the system maintains incrementally.

One-sentence pitch: codoc is a living table-of-contents for your codebase that never goes stale.

The tree.codoc file

After codoc init, the file lives at .codoc/tree.codoc. It's a plain-text indented outline you can read and edit directly in VS Code:

- Authentication flow  ⟨f-3a9c2e⟩
    Handles login, session creation, and token lifecycle.

    Cites [session creation](codoc:auth.py#AuthManager.create_session).

  - Token rotation  ⟨f-7b1d04⟩
      Refreshes session tokens before expiry.

  - Password reset  ⟨f-cc90f1⟩
      Lets a user reset a forgotten password via an emailed one-time token.

  ~ Legacy HTTP Basic auth  ⟨f-2c8b01⟩
      Deprecated in v3; removed from all production paths.

- Notification dispatch  ⟨f-1f88aa⟩
    Queues and flushes email + in-app notifications.

Each - line is a live feature. ~ marks a retired feature (struck-through in VS Code). Indentation (2 spaces per level) determines the hierarchy. The hidden ⟨f-…⟩ id is the stable identity that survives renames — the VS Code extension renders it invisible. Inline [label](codoc:file.py#symbol) links are the only way to cite code; derived bindings are shown as inlay chips, not written into the text.

Day-to-day workflow

1
Initialize. Run codoc init in your project root. This indexes the repo (incrementally — a killed run resumes from the last completed file), proposes a hierarchy, and writes .codoc/tree.codoc. Open the file in VS Code.
2
Read and refine the tree. Rename things, fix descriptions, restructure the hierarchy — edit the file like any text document. The initial tree is a good starting point; intent is yours to author.
3
Start the daemon. Run codoc watch. It watches both code files and tree.codoc, reacting to changes in either direction.
4
Code. Modify source files. codoc detects changes, auto-applies safe updates (re-attach a moved symbol, tweak a description), and places structural proposals in-situ in tree.codoc.
5
Edit the tree. Change a description, rename a node, or add a new one. codoc builds a coding directive and spawns claude -p to implement the corresponding code change, then reflects on the result.
6
Review proposals. Proposals appear inline at their target position in the tree. Click Accept or Reject in the VS Code CodeLens — no text to type.

Proposals: the in-situ review loop

codoc never changes the feature tree without your approval. Instead it places diff hunks at the exact tree position where the change would land:

- Authentication flow  ⟨f-3a9c2e⟩
    Handles login, session creation, and token lifecycle.

+ - Rate limiting  ⟨e-9f01c2⟩
+     Caps API requests per user per minute.

  - Token rotation  ⟨f-7b1d04⟩

A + line (green tint) is a proposed addition. A - line (red tint) is a proposed retirement. A ~ line (blue tint) is a proposed move or amendment. Each block ends with a blank line. The ⟨e-id⟩ identifies the pending event — you never type it.

Use the Accept / Reject CodeLens buttons that appear above each block, or Accept all / Reject all in the header. Verdicts are written to .codoc/inbox.json; the daemon applies them and removes the blocks on the next write cycle.

No text syntax. The old ?→+/- character-swap syntax no longer exists. Proposals are read-only diff views; all interaction is through the CodeLens buttons.

Claude Code integration

codoc integrates with Claude Code through hooks and a skill file — not an MCP server, not a VS Code plugin, not an SDK. There is no server process and no port. codoc init installs both automatically into the repo's .claude/ directory.

ComponentLocationWhat it does
Hooks .claude/settings.json Fire on SessionStart, Stop, PreToolUse, PostToolUse. Maintain .codoc/activity.json — the live agent touch log (which files Claude read/wrote, which features they belong to). Never blocks the agent; exits zero on any error.
Skill .claude/skills/codoc-intent/SKILL.md Auto-loaded by every Claude Code session in the repo. Instructs Claude to express code changes as codoc proposals first (via codoc propose), never touching code until the user Accepts.

Two distinct Claude invocations:

  • Interactive session — you open Claude Code and ask it to add or change a feature. Claude reads the skill, runs codoc propose … (a CLI call that creates a pending Event and re-renders tree.codoc), and waits. It does not edit code files during planning.
  • Headless implementation — after you Accept a proposal in VS Code, Loop B spawns claude -p --dangerously-skip-permissions once with a coding directive. This is a separate, non-interactive invocation; it implements the accepted intent and exits.

The propose-then-implement loop step by step:

1
You ask Claude Code — "Add rate limiting to the auth module."
2
Claude proposes (no code touched). Reads codoc-intent skill → reads tree.codoc to understand existing structure → runs codoc propose add_node --title "Rate limiting" --description "…" --parent f-3a9c2e. An in-situ + - Rate limiting block appears in the file. Claude tells you to Accept in the IDE.
3
You review and Accept. Edit the description in the proposal block if needed. Click Accept in the VS Code CodeLens. Verdict → .codoc/inbox.json.
4
Loop B implements. Drains inbox.json, applies the op to the store, builds a coding directive from the accepted description + bound symbols, sets status.json = realizing, spawns claude -p once, waits for exit.
5
Loop A re-reflects. Runs scoped to the files the agent wrote. If the code matches intent cleanly → status → in_sync. If the implementation revealed something the description didn't capture → additional proposals surface in tree.codoc for the next review cycle.
Installation is one command: codoc init is idempotent — it deep-merges the hook block into .claude/settings.json without clobbering other hooks, and writes the skill file. Safe to re-run after cloning.

VS Code experience

Dependency focus dimming. When your cursor rests on a feature that has call/import edges to other features, that feature and all its graph-neighbors stay full-opacity. Everything else dims to 0.6. The dimming clears instantly when you move to a leaf with no edges, or when you start typing. Toggle with codoc.focusDependencies.

Tree-native keyboard navigation. In tree.codoc, use ⌘K ↑ / ⌘K ↓ to hop between siblings, ⌘K ← to jump to the parent, and ⌘K → to jump to the first child. Normal arrow keys still edit text. ⌘Shift+[ / ⌘Shift+] fold/unfold the subtree under the cursor.

Sidebar feature panel. The codoc Features panel in Explorer shows the full hierarchy. Click any item to jump to its exact line in tree.codoc. Each item shows a binding count (e.g. 3 refs) and a state-aware icon (live / retired / has proposal).

Ref navigation. Click any [label](codoc:file.py#symbol) link: the target code opens in a split pane beside the tree editor with focus preserved in the tree. The target symbol is revealed and briefly highlighted. Stale refs (symbol moved or deleted) show a graceful warning.

Source CodeLens. In every .py or .ts file, a CodeLens label above each def/class/function shows which feature owns that symbol. Click to navigate back to the feature in tree.codoc. Only symbols with an actual attribution are labeled — no noise for unattributed code.

Agent activity. While codoc watch is running and the coding agent is writing code: gutter markers appear on feature title lines in tree.codoc, and Explorer file badges mark touched source files. Both clear when the agent epoch closes. Toggle with codoc.agentGutter.

Proposal styling. Add proposals glow green, retire proposals red, move/amend blue — using a left-border accent and a whole-block background tint. The retired node strike-through and proposal coloring never conflict (proposal blocks are excluded from the strike scan).

Part 2 — Architectural deep-dive

User edits tree.codoc User edits source code │ │ ▼ ▼ Loop B — codoc → code Loop A — code → codoc drain inbox.json verdicts update_index (cocoindex) parse + diff tree.codoc compute_changeset apply user ops immediately auto-ops (REFRESH/ATTACH/DETACH) build directive relocation detection (no LLM) spawn claude -p once one LLM pass for structural ops re-run Loop A on written files structural ops → pending Events │ │ └──────────────────┬──────────────────┘ │ ▼ Store (SQLite WAL) features · bindings · events │ ▼ render.py → write_tree tree.codoc + tree.bindings.json (atomic tmp→rename)
Central design: the store (SQLite) is the single source of truth. tree.codoc is a rendered view of it — not a database replica. Loop A and Loop B both write the store; write_tree renders it back to disk. The extension reads the rendered files; no HTTP, no server process.

Data model

Core types live in codoc/model/:

TypeKey fieldsNotes
Feature id, title, description, parent_id, retired, created_at, updated_at Stable identity via id (f-xxxxxxxx). One prose field: description. No status, no state enum — state is never stored.
Binding id, feature_id, file, symbol_path, fingerprint Links a feature to one code chunk. UNIQUE(file, symbol_path) — a chunk binds to at most one feature. fingerprint = tokens_hash for staleness detection.
Event id, at, source, op, applied, accepted_at Append-only log entry. applied=False = pending proposal. Accepting flips it and runs the op.
NodeOp kind, feature_id, parent_id, title, description, bindings, rationale The payload of an Event. Safe kinds: ATTACH DETACH REFRESH AMEND. Structural: ADD_NODE MOVE_NODE RETIRE_NODE.
HLC logical_time, wall_clock, node_id Hybrid Logical Clock — lexicographically sortable, causal. Used for created_at/updated_at/at everywhere.

Three authoritative SQLite tables: features, bindings, events. One derived cache: code_edges(src_symbol, dst_symbol, kind, internal) — safe to drop and rebuild from the chunk index.

Loop A — code → codoc

Triggered whenever source files change. Five phases:

  1. Index update. update_index (cocoindex + LanceDB) re-parses changed files via tree-sitter, embeds AST chunks, upserts to LanceDB. Memoised per file — unchanged files cost nothing.
  2. Changeset diff. compute_changeset reads the old and new snapshots from LanceDB, keys by (file, symbol_path), compares tokens_hash → ChangeSet{added, removed, modified}.
  3. Auto-ops. derive_auto_ops resolves trivially-safe changes (modified-bound → REFRESH, removed-bound → DETACH) with no LLM.
  4. Relocation detection. _detect_relocations pairs removed↔added chunks that are the same code relocated: a move (identical tokens_hash) or a rename (same-file unique types_hash). Each match emits an ATTACH to the removed chunk's feature — no LLM, no risk of lost attribution.
  5. LLM pass. Only if there are still-unbound additions or a feature lost its last binding. One propose_tree_update call with the change set, a file-locality seed subtree, and every node title (de-dup context). Safe ops apply immediately; structural ops become applied=False Events rendered as proposals.

Coverage net: _cover_uncovered_adds ensures no added chunk is silently dropped — it attaches to the neighbor_feature (graph-neighbor feature with the most call/import edges to the new symbol) or, failing that, surfaces a pending ADD_NODE proposal.

Loop B — codoc → code

Triggered when tree.codoc changes (user edits) or when inbox.json has new verdicts (user Accept/Reject in the IDE).

  1. Drain inbox. For each verdict in inbox.json: accept → apply_op + mark event applied; reject → delete event. Clear the file.
  2. Parse + diff. Parse tree.codoc with parse.py, diff against the store with diff.py → list of user ops (title edits, description edits, new nodes, retires).
  3. Apply immediately. User edits are intentional — applied to the store without a proposal step.
  4. Build directive. For each code-implying op (a description edit with bound symbols, a new node), render a coding prompt from prompts/realize.txt.
  5. Realize. Write status.json = realizing, spawn claude -p … --dangerously-skip-permissions once, wait.
  6. Re-reflect. Re-run Loop A scoped to the files the agent wrote — surfaces any refinements the under-specified intent missed.

File format and round-trip invariant

The key correctness property: render → parse → diff is always a no-op.

This is enforced by identifying proposal blocks via their ⟨e-id⟩ (event id) vs the ⟨f-id⟩ on live features — both parsers (parse.py and the TypeScript tree-model.ts) skip proposal blocks entirely. The diff step only sees live features, so a round-trip produces zero ops.

tree.codoc on disk after a propose_add:

- Authentication flow  ⟨f-3a9c2e⟩
    Handles login, session creation, and token lifecycle.

+ - Rate limiting  ⟨e-9f01c2⟩       ← proposal block (skipped by parser)
+     Caps API requests per user per minute.

  - Token rotation  ⟨f-7b1d04⟩       ← live node (parsed normally)

In-situ proposals render at their target position: ADD proposals under their proposed parent, RETIRE/AMEND proposals immediately beneath the target node, MOVE proposals at the destination. A col-0 op char (+/-/~) + the node indented to its tree depth + ⟨e-id⟩, blank-line terminated. Both parsers are parity-tested against each other on real trees.

Sidecar and dependency graph

render.py writes two files atomically (tmp → rename) on every write_tree call:

tree.codoc — the human surface. Features, descriptions, inline refs, and in-situ proposals.

tree.bindings.json — the IDE sidecar. Schema version 2:

{
  "version": 2,
  "by_feature": { "f-id": [{"file": "auth.py", "symbol": "auth.py::AuthManager.login"}] },
  "by_file":    { "auth.py": [{"symbol": "...", "feature_id": "f-id", "feature_title": "Authentication flow"}] },
  "features":   { "f-id": {"title": "Authentication flow", "parent_id": null} },
  "feature_edges": {
    "f-id": [{"to": "f-other", "weight": 4, "kinds": ["call"]}]
  }
}

feature_edges (new in v2) aggregates code_edges into feature-level call/import coupling — sym2feat maps each bound symbol to its feature, and edges between features are counted and typed. The extension reads this to build an undirected adjacency map for dependency dimming. The extension tolerates the absence of feature_edges (old v1 trees have no dimming).

Three additional files written by the loops, not by write_tree:

  • status.json — {state, pending, detail, at}; state ∈ {in_sync, code_drift, tree_dirty, realizing}. Drives the IDE status bar and the header CodeLens.
  • inbox.json — {version, verdicts:[{event_id, accept}]}. The verdict channel: the IDE's Accept/Reject writes here; Loop B drains and clears it.
  • activity.json — per-file agent touch log: {epoch:{open}, touched:{file:{mode, feature_ids}}, recent:[]}. Drives the agent gutter markers and Explorer file badges.

Extension architecture

The VS Code extension (vscode-codoc/src/) is entirely file-based. No HTTP client, no server process, no port.

State layer

  • state/workspace-state.ts — root detection, file watchers on all five .codoc/ files, reload on change, fires onDidChange; status bar; writeVerdict() appends to inbox.json.
  • state/tree-model.ts — TypeScript port of parse.py, parity-tested. Parses features, proposal hunks (with endLine for block coloring), inline refs.
  • state/bindings-model.ts — sidecar types, entriesForFile, bindingsForFeature, and featureAdjacency() which builds the undirected adjacency map from feature_edges.

Provider layer

  • providers/decoration.ts — hides ⟨…⟩ ids (display:none); colors in-situ proposal blocks from parser ranges (not per-line regex); strikes retired live nodes (excludes proposal lines from the strike scan).
  • providers/focus.ts — dependency dimming: selection listener + 400 ms debounce + undirected adjacency map → dims complement at 0.6 opacity; clears on blur or cursor on edge-free node.
  • providers/agent.ts — static gutter marker on activity.json activeFeatureLines.
  • providers/file-decoration.ts — Explorer file badges on touched source files.
  • providers/inlay.ts — derived-binding chips at the end of each feature title line.
  • providers/codoc-tree-lens.ts — header status + per-proposal Accept/Reject + Accept all / Reject all.
  • providers/code-actions.ts — lightbulb Accept/Reject on hunk lines.
  • providers/code-lens.ts — source-file CodeLens: owned symbols → feature name + navigate.
  • providers/feature-tree-view.ts — sidebar tree: click → precise line jump; binding count; state icons; cursor↔selection reveal sync.
  • providers/{folding,symbol,feature-lines,completion,doc-links}.ts — outline, fold, nav helpers, [-triggered ref autocomplete, clickable codoc: links.
Watcher coverage: WorkspaceState watches **/.codoc/{tree.codoc,tree.bindings.json,status.json,inbox.json,activity.json}. Every write by the daemon fires onDidChange and all providers update synchronously — no polling, no HTTP round-trips.
Self-write guard: watch.py tracks the last time it wrote tree.codoc and ignores FS events that arrive within a short window after its own write. This prevents the daemon from triggering itself in a loop when it re-renders the tree after applying ops.
