# 4. System Design

## 4.1 Overview

codoc is a Visual Studio Code extension that maintains a *feature tree*, a human-authored hierarchy of named intents, bidirectionally synchronized with the code of a repository. Each node is a feature, a named unit of what the code is *for*, linked to the specific code chunks that implement it across many files. Unlike literate programming, where explanation drifts as soon as others change code, the feature tree is maintained continuously by machinery. Two synchronization loops keep the tree and the code aligned. One reflects code changes into the tree as visible proposals. The other realizes tree edits into code through the developer's live coding-agent session.

The tree renders as a scrollable prose document within the IDE's editor pane rather than as a tree widget or a tool window. A collapsible tree widget hides most nodes by default, so a proposal nested three levels deep goes unseen until the developer expands that subtree. An outline sidebar competes with file explorer and source control for the same panel slot and loses whenever the developer opens source control to review diffs. The prose document won because a map of intent needs to be *read top to bottom* the way a person reads a table of contents.

## 4.2 Walkthrough, Reviewing an Agent's Change

To illustrate how codoc serves a developer in practice, we follow a task from our evaluation study, namely reviewing a change that a coding agent made to an unfamiliar project.

**Orientation.** Sam opens a project they have never seen, a document-formatting tool of four thousand lines across two dozen files. They open `tree.codoc`. The feature tree shows the system's shape in a page of prose, with a *report formatter*, a *page layout engine*, a *cross-reference resolver*, and a *CLI driver*, each carrying a short description and inline links to implementing code.

**Seeing proposals.** An agent session modified the project, adding a configuration layer and changing margin computation. A new child feature called "Margin override settings" appears as a *proposed addition*, rendered at its claimed position and visually distinct from committed nodes. On the cross-reference resolver, an *amend proposal* shows the old and new description side by side. Each proposal waits for a verdict.

**Deciding.** Sam accepts the margin-override proposal, a single action that applies the operation to the store, records the verdict in the ledger, and solidifies the node in the view. On the cross-reference amendment, the description claims deferred resolution but the tests still assert single-pass. Sam rejects. The old description stays and the feature's status shifts to *code drift*. Rejection means "I do not agree that the tree should look like this," because the code might be correct and the description might need updating instead.

**Noticing discrepancies.** The drift marker appears on the feature itself. The agent introduced a behavioral change too small for a proposal, but the drift status catches it because the content hash no longer matches the stored fingerprint. Drift is distinct from a proposal because the two serve different cognitive functions. A proposal demands a verdict. A drift marker demands investigation. The boundary is structural significance. Making every discrepancy a proposal would flood the developer, training them to click Accept without reading. Making every discrepancy silent would hide the behavioral shifts that matter most.

**Directing a correction.** Sam selects the sentence asserting single-pass resolution and types an inline comment saying "revert to single-pass and fix the margin lookup to not require deferred access." The comment is scoped to the selected prose span rather than to the whole feature, because a description carries several claims and scoping to the span tells the agent which assertion to honor. The comment becomes a *steer directive* scoped to the feature's bound code. The agent implements the correction and Loop A reflects the result back.

## 4.3 How Mechanisms Address Design Goals

The walkthrough illustrates how the five goals compose. G1 faithfulness made Sam's verifications meaningful. G3 orientation depended on G1, because a two-page prose summary is only an orientation tool if the reader trusts it. G2 change visibility created the encounter that made Sam decide, but proposals only carry weight because the representation around them is faithful. G4 communication let Sam direct a correction at intent scope rather than file scope. G5 durability followed from the accept and reject being the same operation as deciding. The goals form a dependency chain in which faithfulness is the foundation and durability is a structural consequence of how decisions enter the system.


# 5. Architecture

## 5.1 Data Model

Four structures compose the system's state. A *chunk set* parses the repository into AST-level units, each carrying a content hash that detects moves and a shape hash that detects renames, reparsed incrementally on each file save. A *feature tree* holds features under a forest-shaped parent relation, with titles and descriptions as free prose, never regenerated from code. A *binding map* links each chunk to at most one feature, storing the chunk's content hash as a fingerprint so staleness is locally detectable. And a *change ledger* records every mutation as an append-only event carrying the operation, its target, its actor, and a causality link to the directive it implements. Proposals are unapplied events. Accepting one applies the operation and consumes the event.

The "at most one feature" constraint in the binding map is the hardest design decision and the one we reconsidered most often. A many-to-many mapping would model reality more faithfully, since a function that handles both serialization and validation arguably belongs to two features. We chose one-to-one because it makes verification local. If a chunk can belong to multiple features, changing that chunk requires updating multiple descriptions, and verifying a single feature no longer guarantees that its bindings are exclusive. The developer cannot check one feature in isolation, and the induction step that makes trust formation rational breaks. The trade-off is that some chunks sit at a boundary and are assigned to whichever feature exercises them more. That assignment can be wrong, and when it is, the developer sees an irrelevant binding rather than a missing one. We judged this failure mode less dangerous than undermining the locality property that makes two-check trust formation possible.

## 5.2 Loop A, Code to Tree

Loop A reflects code changes into the tree. Its design principle is *determinism first*. Every change that can be resolved mechanically is resolved without a model call, and only the residual goes to a single LLM pass per cycle. The reason is correctness rather than efficiency. A content-hash comparison is correct by construction. A language model seeing "function disappeared from file A, appeared in file B" may propose to retire one feature and add another when the correct operation is a move. Deterministic operations apply first: refreshing fingerprints on modified chunks, detaching removed chunks, and re-attaching chunks whose content hash reappears at a new identity. If a residual remains, a single LLM call receives the changeset and *every feature title* together. The call must be global because deduplication is wrong when local. A per-file call sees "function disappeared" and "function appeared" separately, proposes a retire and an add, and the tree doubles. We tried per-file calls in an early prototype and watched a single refactoring generate four duplicate features. The cost of a missed deduplication is uniquely poisonous to trust formation. A duplicate claims the same code as its twin, and the developer who verified feature A encounters A' asserting the same bindings, collapsing the induction that made trust rational. A false deletion is recoverable from version control. A duplicate is unrecoverable without the developer's memory of which was authored and which was hallucinated.

The model's output is not trusted with destructive authority. Safe operations apply automatically because an incorrect fingerprint refresh is caught and corrected on the next cycle. Structural operations become proposals requiring a human verdict because an incorrect deletion is irreversible without the developer's memory of what was there. The deeper reason is trust rather than recoverability. Silent structural changes are precisely what breaks the trust threshold described in Section 8.1. A developer who returns to find that a feature was retired without their knowledge learns that the tree rearranges itself behind their back, and the rational response is to stop trusting it. The proposal mechanism exists to make the tree's behavior predictable enough that behavioral trust can form.

## 5.3 Loop B, Tree to Code

Loop B drains human edits and verdicts from the tree. Where those imply a code change, it assembles directives for the developer's live coding-agent session.

An accepted proposal applies its operation and mints a *directive*, a work order assembled from the feature's description and bound symbols. Human edits are classified by an *imperative gate* where descriptive prose merely persists while imperative prose or a comment mints a directive. The alternative is explicit syntax, a marker that says "this is an instruction." We rejected that because it creates what Green and Petre [1996] call *premature commitment*, forcing the developer to classify their intent before expressing it. In pilot use, developers facing that two-mode choice defaulted to documentation mode exclusively and never issued directives through the tree, leaving the representation readable but inert as a communication channel. Instead the system infers intent from form. "Retry logic backs off exponentially" is a description of desired state. "Add exponential backoff to retry logic" is an instruction.

The gate can err in both directions. We bias it toward false negatives because surprising action is worse than surprising inaction. A developer who writes an imperative and gets no response will simply rephrase, a recovery that costs seconds. A developer who writes a description and triggers unexpected code changes learns that the tool acts on their words unpredictably, which is precisely the loss of control that damages trust in the representation. The asymmetry is that false negatives teach the developer the representation is occasionally unresponsive, while false positives teach them it is dangerous to write into. Directives queue for the live session and Loop A reflects the resulting code changes to close the cycle.

## 5.4 How the Architecture Enables Rapid Trust Calibration

The three properties from Section 2.3 pull in different directions. Maintenance wants to overwrite human edits with current state. Editability wants to pause automation so edits are not immediately consumed. Operativity wants formal precision so the system can translate intent into action. Holding all three simultaneously is what makes the trust threshold possible.

A developer forms behavioral trust by verifying a small sample and generalizing. That generalization is only rational if the verification infrastructure applies uniformly. Three mechanisms produce that uniformity.

The *hold set* prevents maintenance from overwriting human edits. When a developer is mid-thought on a feature, that feature enters the hold set and Loop A leaves it alone while continuing to maintain everything else. The hold is scoped to the feature rather than to the whole tree, so automation continues around the edit rather than blocking on it. A whole-tree hold would let unmaintained descriptions accumulate staleness during every edit, invisible to the developer who triggered the pause.

The *imperative gate* described in Section 5.3 resolves the operativity tension without formal syntax. The representation remains natural language that a developer can read and verify against code in seconds.

The *continuous synchronization loops* resolve the maintenance tension by being incremental and deterministic. Each code change produces a bounded delta, and the system can tell the developer whether what they read is current because it knows exactly when each binding was last verified. Determinism means the same verification that worked once will work again.

These mechanisms map directly to the three trust conditions from Section 8.1. Locality holds because each feature's binding map is self-contained, so verifying feature A requires reading only feature A's code. Uniformity holds because the loops use a single mechanism, content-hash comparison, on every binding without exception, so confirming the mechanism on feature A provides evidence about feature B. Cheapness holds because verification is a link click followed by reading a bounded code region scoped by the binding. A documentation tool with manually authored hyperlinks provides locality but not uniformity, because each link is maintained independently and there is no guarantee that what makes link A correct has anything to do with what makes link B correct.

The conditions were design predictions, not post-hoc rationalizations of the evaluation. The architecture was built to satisfy them before Study 2 ran, on the hypothesis that if verification is local, uniform, and cheap, trust will form rapidly. The evaluation tests whether the predicted behavioral shift occurred, not whether the conditions are the correct explanation for it.
