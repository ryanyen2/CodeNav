# 2. Related Work

Three bodies of work converge on the problem codoc addresses. The first is the recurring effort to hold a codebase in terms of its intent, explaining why the problem resisted solution for forty years and what recently changed. The second is shared representations between humans and machines, which supplies the design logic but has never been applied at codebase scale where persistence and trust are load-bearing. The third is the growing challenge of understanding code that an AI agent produced, which establishes urgency and identifies the precise gap in existing tooling.

## 2.1 The Intent-Code Gap from Literate Programming to Agent-Era Documentation

Knuth's [1984] literate programming kept prose and code consistent at the moment of writing but said nothing about maintenance, so the explanation went stale as soon as someone else changed the code. The concept assignment literature [Biggerstaff et al., 1993; Rajlich & Wilde, 2002] formalized the underlying problem. A change is stated in domain concepts, but where those concepts live in the code is unknown, and one concept usually spans many files. Tools for locating concept-to-code mappings [Dit et al., 2013] ran once per task and returned ranked lists that were never maintained. Approaches that made intent the primary artifact, including intentional software [Simonyi et al., 2006] and projectional editors [Voelter et al., 2014], required specialized editors that broke diff and version control, and the adoption threshold was prohibitive.

Today the same goal returns in agent-era tooling in three forms. The first keeps a natural-language artifact beside the code. SpecLang [GitHub Next, 2023] treats a program as a prose specification the model compiles, while Cursor rules [2024] and Cline's memory bank [2025] persist conventions for the agent to reload. These make the agent more controllable, but the artifact has no binding to the code it governs. A Cursor rule says "always use TypeScript strict mode" but cannot detect that three files were added in lenient mode last week. A second form conditions generation on documentation. DocPrompting [Zhou et al., 2023] retrieves library docs and DocCGen [Pimparkhede et al., 2024] constrains against structured docs. A third builds an intermediate structure. RPG [Microsoft Research, 2025] plans a repository as a capability graph, and CoLadder [Yen et al., 2024] decomposes tasks hierarchically. All three improve code produced *from* a description, but the description is consumed once rather than persisting as a living representation. The recurrence is not coincidental. Each form optimizes for a single generation event because the engineering cost of maintaining a binding between prose and code across subsequent edits is qualitatively harder than producing code from prose once, so tool builders stop at the boundary where maintenance would begin.

Across these efforts, two obstacles recur. Keeping the map current was manual labor, so it rotted. And editors that made intent primary were too specialized to adopt. What has changed is that a language model can re-derive what each part of the code does cheaply enough to run continuously, on every file save rather than once per release. This collapses the first obstacle. A tool that re-derives on every save has no staleness window, so a single verified check remains valid until the next code change rather than degrading on a schedule the developer cannot see. The second obstacle remains. A representation that an LLM maintains still needs to be something a developer reads, trusts, and edits without specialized tooling.

## 2.2 Shared Representations Between Humans and AI

Heer [2019] argues that the most productive human-AI systems work through shared representations, a common medium both parties read, modify, and reason about. Chat is readable but not operative. Code is operative but not readable at the intent level. A shared representation combines both properties. Several systems demonstrate this in bounded interactions. Wrangler [Kandel et al., 2011] creates shared representations for data transformations, text-to-SQL tools [Tian et al., 2023] for editable queries, Liu et al. [2023] for code-to-NL intermediaries, and CoPrompt [Feng, Yen et al., 2024] for prompt construction. Each creates an artifact simultaneously editable by the person and operative for the machine, but each is scoped to a single interaction. The transition from bounded to persistent changes the engineering problem qualitatively. A fresh representation is always correct because it was just generated, and its failure mode is local. A persistent representation fails differently because its failure mode is contamination. If one description drifts out of sync, the developer does not learn which one, only that "somewhere in this document, something is wrong." The rational response is "none of this can be trusted," which means a single staleness failure poisons the entire artifact. This contamination property is what makes the engineering of persistent shared representations fundamentally harder than rerunning bounded ones.

Shipman and Marshall [1999] identified the tension that makes codebase-scale representations hard. Formality enables automation but informality enables expression. Henderson [1991] observed the same in engineering practice, where designers prefer informal sketches because sketches tolerate the ambiguity needed during active design. Systems that formalized everything gained automation but lost informal expression. Systems that left everything informal gained expression but lost automatable structure. The resolution is not a point on the spectrum but a factoring into two orthogonal layers, one formal enough to synchronize and one informal enough to write naturally. In codoc, the binding map and content hashes are the formal layer that enables automatic maintenance, and the feature descriptions are the informal layer that tolerates the ambiguity needed during active design. Section 3.3 describes how the design arrives at that factoring.

Lee and See's [2004] framework identifies the key condition for managing that contamination risk. Trust requires *observable accuracy*. The developer must be able to verify the map holds. None of the bounded systems above face this requirement because none persist long enough to be trusted or doubted, which is why scaling them to codebase scope requires solving a different engineering problem rather than running them more often. The contamination property also determines the shape of the trust function. Because a single stale description poisons the whole artifact, trust is not proportional to the fraction of correct descriptions but collapses on a single failure, either the maintenance mechanism is believed to work or it is not. The implication for design is that the engineering challenge is not making each description more accurate but making the maintenance mechanism itself verifiable.

## 2.3 Understanding and Reviewing AI-Generated Code

Verification rather than generation dominates how programmers interact with AI coding tools, and the pattern holds across studies with different populations, tools, and measures. Barke et al. [2023] found Copilot users spend most time reading and evaluating suggestions, and Sarkar et al. [2022] described the experience as iterative evaluation against mental abstractions. These two findings together establish that the bottleneck is not producing code but deciding whether produced code matches the developer's unstated intent. Mozannar et al. [2024] showed the validation overhead can exceed productivity gains when generated code is large, which means the problem worsens precisely as the tool becomes more capable. Vaithilingam et al. [2022] confirmed that even correct code is frequently hard to verify, leading to over-reliance or rejection. Huang et al. [2025] found experienced developers retain agency over design decisions *out of insistence on fundamental software quality attributes* rather than distrust of agent output. The implication is that oversight is not transitional. Developers who care about quality need a surface through which to exercise judgment regardless of how correct the generated code is, because correctness and desirability are different properties.

At codebase scale, these challenges compound. Individual generations accumulate into an evolving system where architectural decisions, made implicitly across interactions, become difficult to trace or revise. Prather et al. [2023] observed that developers lose track of what the system added, unable to explain code in their own files. Zhang [2025] names this *comprehension debt*, the gap between what the codebase does and what the developer understands, which grows with each AI-generated change and accrues interest until a crisis forces repayment.

Several approaches make the agent's reasoning transparent at the moment of generation. ClarifyGPT [Mu et al., 2024] asks clarification questions before generating, and step-by-step explanations make individual outputs reviewable. Yet all are episodic. They illuminate one generation, then disappear into chat history, saying nothing about what the codebase *is* after fifty such interactions have accumulated.

The gap is not "a better documentation tool." No artifact exists which is simultaneously maintained by machinery so it does not rot, editable by a person so it expresses their intent rather than the machine's summary, and operative so that editing it changes what the agent does next. Existing tools deliver at most two of these three. Agent-era documentation such as CLAUDE.md is maintained and operative but not human-editable; the agent rewrites it to match its own work, so a human edit is overwritten on the next pass. Traditional documentation is editable but not maintained, and the history of software engineering is a graveyard of design documents abandoned after their first quarter. Shared representations are editable and operative but scoped to one session, because no one has built the engineering to keep a mutable representation consistent with an evolving codebase across hundreds of sessions.

Schmalbach [2026] provides independent evidence that operativity alone is insufficient. Documentation artifacts appeared "mostly or only when explicitly demanded" by the contract structure. A representation that no one is forced to engage with cannot accumulate the verified interactions that produce trust.

codoc occupies all three. The engineering challenge is holding them simultaneously because they pull in different directions. Maintenance wants to overwrite human edits with current state. Editability wants to pause automation so edits are not immediately consumed. Operativity wants formal precision that resists informal expression. Section 5.4 describes how three mechanisms resolve these tensions without sacrificing any of the three properties.
