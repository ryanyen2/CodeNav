# 1. Introduction

A developer asks their coding agent to add environment-based configuration to a web API they have been building for two weeks. The agent finishes in four minutes. Fourteen files changed. Three new modules appeared. The tests pass.

The developer comes back the next morning and cannot tell what it did.

The agent's summary says it added a config system with environment-based overrides. That sentence conceals more than it reveals. A timeout function the developer wrote last week, with specific values chosen after a production incident, was absorbed into the new config layer with different defaults. The deployment secrets now load through a different path. None of this is wrong. All of it is invisible. The developer finds themselves re-reading files they thought they understood, reconstructing a mental model of a system that moved without them.

This experience, of knowing the code changed but not knowing what the code *is* anymore, is becoming the default mode of working with coding agents. The 2025 Stack Overflow survey found 84% of developers use AI coding tools while only 29% trust the output. METR [2025] showed why. In a randomized controlled trial, experienced open-source developers using AI tools completed tasks 19% *slower* than without, yet perceived themselves 20% faster. The slowdown came from verification work whose cost remains invisible to the person performing it. Demirer, Musolff, and Yang [2026] found the same gap at organizational scale in a study of 100,000 GitHub developers, reporting that autonomous agents generated 180% more commits but only 30% more releases, the difference consumed by review and integration work that generation speed does not eliminate. Developers skip checking not because they believe the code is correct but because the cost of checking exceeds the perceived benefit per change. Storey [2026] calls the accumulation *intent debt*, the absence of explicit rationale that explains why the system is the way it is. The problem is no longer whether a developer can read a function but whether they can tell what the system is now, how it got here, and what was decided along the way.

## The missing account

Agents do not write bad code. Many write code that is perfectly reasonable in isolation. But the faster they change things, the more a developer's ability to debug, iterate, and evaluate depends on an *account* of the code, a persistent description of what it is and why, that nobody maintains. Bainbridge [1983] identified the fundamental irony of automation. The more reliable the system, the less the operator monitors, and the less capable they become of intervening when the system eventually fails. A developer who stops reading code because the agent is usually right has no mechanism for noticing the cases where it is not.

There are artifacts that look like they fill this role. A CLAUDE.md says "The playlist module handles fetching, caching, and displaying playlists" but nothing about why caching is client-side. Cursor rules say "always use TypeScript strict mode" but cannot detect violations. A Cline memory bank records "auth was refactored to use JWTs" but cannot say whether that refactoring preserved session-timeout behavior. Each artifact fails for the same structural reason. The writer is the agent, the audience is the agent, and the developer is neither. Treude and Baltes [2026] measured this across 356 repositories and found stale code references in 23% of AI configuration files, a phenomenon they call *context rot*. The rot is predictable. An artifact without bidirectional synchronization drifts toward serving its most frequent writer, and the most frequent writer is always the model. The model rewrites CLAUDE.md after each action and populates the memory bank between sessions. A person edits at best occasionally, and that edit is overwritten on the next pass. The asymmetry is not a bug in any particular tool but a consequence of letting one party own both writing and reading.

No existing surface lets a developer see what a codebase is at the level of intent and know that what they see is faithful to the current code. LaToza and Myers [2010] catalogued the questions developers struggle with, and all concern WHY rather than WHAT. What is needed is a representation that is faithful, readable as a map, editable to express what should change, and operative so that editing it causes code to change. Without operativity, maintaining the representation is preparation for work rather than work itself. A developer who edits a description to say "retry logic should back off exponentially" has done the conceptual work, and the operative property translates that into implementation without requiring a separate step in a different tool.

## Prior attempts at maintaining intent

Four decades of tools have tried to hold codebases in terms of their intent. Literate programming [Knuth, 1984] assumed a single author and therefore no maintenance problem. Concept assignment [Dit et al., 2013] located intent-code mappings but never maintained them, so they rotted between queries. Intentional software [Simonyi et al., 2006] and projectional editors [Voelter et al., 2014] made intent primary but broke the developer's existing toolchain. Agent-era documentation persists text without synchronizing it to code, and shared representations [Heer, 2019] work within a single interaction but have never been sustained across a codebase's lifetime. Section 2 traces why the same failure recurs. The common factor is that binding prose to code across subsequent edits is qualitatively harder than binding it once, and every system stopped at the boundary where maintenance would begin.

## codoc, an editable map of intent synchronized with code

codoc maintains a *feature tree*, a hierarchy of named units of intent, bidirectionally synchronized with the code of a repository. A developer reads it to understand the system, edits descriptions to express what the code should be, reviews the agent's changes as proposals within it, and directs work through comments scoped to specific features. The agent implements intent expressed in the tree and surfaces its changes back as visible, reviewable proposals.

Two design insights, earned through iteration, distinguish codoc from what preceded it. First, the representation must serve as a **communication layer** rather than a specification language. An earlier version studied with 12 developers worked as an orientation map but failed as a communication medium because its file-level syntax could not express what developers think in, namely what the code *should be* rather than step-by-step plans for changing it. The redesigned system lets them describe intent at the level of *features*, cross-file units of purpose.

Second, the value of the representation depends less on its expressivity than on its **trustworthiness**. Once a developer verifies that the map corresponds to the code, they stop opening files and reason from the representation alone. This *trust threshold*, the moment the representation becomes reliable enough to navigate by, is what makes the system useful. The synchronization loops that keep the map faithful matter more than the editing surface.

A second within-subjects study with 12 developers evaluates whether the redesigned system delivers on its promise when reviewing changes an agent has already made.

## Research questions

Given a codebase representation designed as a synchronized communication layer between developer and agent, we ask three questions.

**RQ1.** How do developers use a synchronized intent representation when reviewing and directing changes an agent made to a codebase? This is exploratory, targeting strategies, appropriation, and communication patterns.

**RQ2.** Does a synchronized intent representation improve a developer's ability to detect and attribute changes in agent-generated code, compared to standard maintained documentation? This is confirmatory, targeting detection coverage.

**RQ3.** Does working through an intent representation produce more durable decision records than working through chat and companion documents? This is confirmatory, targeting durable written trace.

## What we found

After an initial pass verifying the tree against code, participants crossed what we call the *trust threshold*, the behavioral shift from "I will check the code to confirm" to "I will make my next decision based on what the tree says." That shift occurred after verifying two or three features and finding them accurate, each check taking seconds because a binding scopes verification to a bounded code region. Once across, participants stopped opening source files and reasoned from the representation alone. Detection coverage was higher with codoc than with the maintained-documentation baseline. Decision records persisted in the change ledger rather than disappearing into chat. The representation worked not because it was expressive but because it was faithful, and once faithful, trust restructured the entire task from exhaustive verification to targeted inspection.

The contributions are twofold. First, an architecture holding three properties simultaneously, machine-maintained, human-editable, and operative, that prior systems achieved at most two of. Second, pre-registered evidence from a within-subjects study with 12 participants that this architecture produces a behavioral shift from exhaustive verification to targeted inspection, with higher detection coverage and more durable decision records than the maintained-documentation baseline. The connecting principle is that the verification crisis described above is not a problem of insufficient expressivity or model capability but of verification cost. When the cost of checking one claim drops below the threshold at which checking becomes default behavior, developers check, trust forms, and the representation becomes the medium they work through rather than one more thing to verify.
