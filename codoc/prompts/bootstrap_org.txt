## How work flows through this codebase (main call paths)

{flows}

- Each line follows one operation inward from where it enters the system,
  through the modules it passes on the way. These are the paths a person has to
  learn to work here, and they matter MORE than the coupling counts above:
  coupling says two things touch often, a path says they are steps in the same
  job, in this order.
- Prefer themes that name a **stage of the work** ("Preparing a request",
  "Sending and retrying") over themes that name a **kind of thing** ("Utilities",
  "Models", "Helpers"). A reader who knows the stages can find anything; a
  reader given a filing cabinet has to open every drawer.
- A feature that appears early in several paths is usually an entry point and
  belongs near the top of the tree, not filed under whatever it happens to call.
- The opposite holds for **housekeeping metadata**: package identity, version
  constants, packaging/build configuration, and similar "what this project is
  called" features go at the BOTTOM of the tree, after everything that says what
  the project does. They read early in files (a module docstring, a __version__)
  but nobody opens a codebase to learn its version string — a reader's first
  screen should be the work, not the label on the box.

## What to do

1. Create a SMALL number of broad **theme** parents so that, after grouping, the
   top level has roughly 3–6 nodes. Group features that collaborate (per the
   coupling above) or share an obvious purpose under the same theme.
2. Keep it SHALLOW: themes at the top, the existing features as their direct
   children. Do NOT nest more than this one new level.
3. It is fine to leave a genuinely standalone feature at the top level with no
   theme. Do not force everything into a theme.
4. Do NOT rename, re-describe, merge, retire, or rebind existing features. You may
   ONLY add theme parents and move existing features under them.

## How to express it

Give each new theme a temporary id (`"id": "t1"`) and `add_node` it with a real
1 to 3 sentence description: the theme's purpose in plain everyday words — what
this group of features accomplishes together, understandable without reading
any code.

Say what the group is *for*; do not narrate decisions or history you were not
shown, and do not hedge with "presumably" or "appears to". Then `move_node` each
existing feature by its real `f-...` id under a theme via `parent_id`.

**Every node you write here is a top-level node with children under it**, which
fixes the register (see "Write at the altitude of the node you are on" below): a
theme's description is the first prose a newcomer reads, and they are reading it to
decide which child to open. So no symbol names, no file names, and no thresholds —
those live in the features underneath. A theme whose description lists its machinery
tells a reader what is there and not what any of it is for.
