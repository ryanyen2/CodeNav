You are writing the first feature tree for the codebase "{repo_name}".

- A feature tree is an outline of what the code is for. Each node, a feature, has a title, a description and the code chunks it owns.
- A chunk is a function, method, class or module-level block, named `file::symbol_path`.
- You see ONE file per call: its chunks and the call and containment relations among them.

Return a small set of features that says what this file is for.

## Choosing features

1. Few. A small or single-purpose file is one feature. Split only when the file does two or more unrelated things.
   - If one feature would own more than about 12 chunks, check that they are one concern. An opening sentence that has to list four subsystems means four features.
   - Two classes that implement the same interface independently (two tokenizer backends) are two features.
2. A class and its methods are one feature. Add a child feature only for a group of methods that is a separable concern.
3. Every chunk listed must be bound by exactly one feature you return.
   - `<file>::__module__` (imports, module setup) goes to the first feature you return, never to a feature of its own. Never describe imports.
   - A module-level constant goes to the feature that uses it most.
4. Do not add a feature whose title paraphrases one in the list of existing titles below.
5. A file with no logic of its own (it only re-exports names, or only lists literal values or type aliases) is one feature with one sentence saying what it is for. Do not list its names.

## Relations

- `calls` / `called_by`: other symbols, some in other files. Use them to judge what belongs together. Never bind a symbol outside this file.
- `contained_in`: the symbol is a member of that class.

## Nesting

Give a feature a temporary id (`"id": "n1"`). A child sets `"parent_id": "n1"`. Parents come before their children.

## Fields

| field | what goes in it |
|---|---|
| `title` | 3 to 6 words, sentence case, a noun phrase naming what the code is for ("HTTP transport adapter"). Never the file name. |
| `description` | Markdown, written as the guide below says. Never empty. |
| `bindings` | the chunks this feature owns, each by its full name `file::symbol_path` as listed below |
| `rationale` | one short line: why this is a feature of its own |

## Evidence for a reason

Three sources count, and nothing else:

1. the brief below, which is what the project says about itself;
2. comments and docstrings in the chunks you are shown;
3. the commit messages below, where one states a reason.

- A source states a reason for a fact you write: add it to that fact as a clause (", because …"). The reader sees the code, not the source, so never name it.
- The code chose between two workable options and a source says which and why: that goes directly after the opening sentence.

## Output

JSON inside solution tags, nothing else. `description` is a JSON string: a line
break is `\n`, and it contains no double-quote character (use backticks around
a literal).
