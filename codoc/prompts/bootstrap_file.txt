You are building the initial **feature tree** for the codebase "{repo_name}" — a
navigable hierarchy of *intent*, where each node is a named unit of what the code
is for and binds to code chunks (a chunk = a function, method, class, or
module-level block, identified by `file::symbol_path`).

You are looking at ONE file at a time. Given the file's code chunks and the
call/containment relationships among them, produce a SMALL, coherent set of
features that captures what that file is for.

## How to choose nodes

1. **Group coarsely — prefer FEW nodes.** A small or single-purpose file is
   usually ONE feature. Only split a file when it clearly does two or more
   unrelated things.
   - **Upper-bound check:** If a single node would own more than ~12 bindings,
     ask whether the bindings represent genuinely one concern. If your description
     needs to comma-list 4+ distinct subsystems (e.g. "config, attention, MLP,
     generation, analysis"), split it — that description is signaling multiple nodes.
   - **Two parallel implementations rule:** If a file contains two classes with
     independent implementations of the same interface (e.g. two different tokenizer
     backends, two different optimizer variants), give each class its own node rather
     than lumping them. They serve different purposes even if they share a protocol.
2. A class and its methods are normally ONE feature (the class). Only break out a
   cluster of methods as a CHILD node when they form a clearly separable concern.
3. **Every chunk listed MUST be bound by exactly one node you emit.** Bind
   module-level chunks (`<file>::__module__`) to the file's primary feature, not a
   node of their own. Bind module-level constants to the node that primarily *uses*
   them, not to a generic utilities node.
4. Do not invent a node whose title merely paraphrases one already created from
   another file (see the list below); name this file's intent on its own terms.

## Relationships legend

- `calls` / `called_by` are other symbols (some in other files) — use them to
  judge cohesion, NOT to bind anything outside this file.
- `contained_in` means the symbol is a method/member of that class.

## Nesting (within this file)

To nest, give each new node a temporary id (`"id": "n1"`) and set a child's
`"parent_id"` to that temporary id. Parents must appear before their children.

## Field rules

- `title`: a 3–6 word sentence-case noun phrase naming the intent ("HTTP
  transport adapter") — NEVER the bare filename.
- `description`: 1–3 short sentences that hand a newcomer the *theory* of the
  feature. Open with its purpose — the problem it solves, in plain everyday
  words a reader who has never seen the code understands. Then, when the code
  shows it, the key design choice and its why (the constraint, failure, or
  tradeoff it answers). No jargon, no restating the title, no lists of code
  locations (bindings carry that). You MAY include AT MOST one inline citation
  `[symbol()](codoc:file.py#symbol)` — file and symbol verbatim from your own
  bindings — when one symbol anchors the claim. Never emit lines starting with
  `> ` or `**bold**` spans (reserved author channels). NEVER leave it empty.
- `bindings`: the `[file, symbol_path]` pairs this node owns.
