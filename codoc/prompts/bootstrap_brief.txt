You are about to write a feature tree for the codebase "{repo_name}": an
outline of what the code is for.

Before any file is described, read what the project says about itself and write
a short brief. Every later pass gets this brief, so that each file is described
as a part of something. This is the only pass that reads the project's own
prose. Later passes read code.

## What you are reading

- the README and the package metadata,
- the module docstring and leading comments of every source file.

Authors write here what the code cannot say: what the program is for, who uses
its output, what it leaves out on purpose, why a rule went one way. Take those
statements as written.

## Fields

| field | what goes in it |
|---|---|
| `purpose` | what the program is for, in one or two sentences: what goes in, what comes out. Define any project term you use. |
| `audience` | who the output is for and what they do with it, when the project says |
| `out_of_scope` | things a reader would expect this program to do that it does not. Only what the project says or clearly implies. |
| `vocabulary` | words this codebase uses in its own way, each with a short gloss |
| `decisions` | choices where another project could reasonably have gone the other way: the `choice`, the reason (`because`) if one is given, and what it costs (`gave_up`) if that is given |
| `ordering` | places the project says one step must run before another: `before`, `then`, and what goes wrong `otherwise` |

`decisions` is the most useful field and the one most often left empty. A rule
stated with a reason is a decision ("the hyphen is dropped, because in a
justified column the typesetter added it"). So is a threshold with a
justification, an order described as mattering, or a stated cost.

## Rules

- Only what the text supports. If the project never says who the output is for, leave `audience` empty.
- Nothing invented: no rejected alternative nobody mentioned, no history nobody wrote down.
- Plain words, short sentences. No filler (robust, seamless, leverage, comprehensive, key).
- An empty field is a correct answer. A short true brief is better than a long one with a guess in it.
- No double-quote character inside any value. These are JSON strings.
