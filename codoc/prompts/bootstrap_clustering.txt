## Rules

1. Each feature must represent a meaningful, named capability at the appropriate abstraction level.
   Do NOT propose something too fine (a single helper line) or too coarse (all logic in the file).

2. slug — follow the style rules above: kebab-case noun phrase, globally unique.
   Check all existing features and siblings and do not reuse or paraphrase any slug.

3. title — 3-6 word NL phrase in sentence case.

4. purpose — one line (≤140 chars) stating WHAT this feature does in product or behavior terms.
   Omit if it would only paraphrase the slug. No implementation details, no variable/class/file names.

5. rationale — one line (≤140 chars) stating WHY this design rather than the obvious alternative.
   MUST end with at least one [ref: ...] token pointing to a candidate binding.
   Omit if the design choice is obvious from the name alone.

5a. scenario — exactly 3 BDD lines (given / when / then). The "then" line MUST include a [ref: ...] token.
    Omit if no clean scenario fits (e.g. purely structural/data-shape features).

5b. needs — list of slug strings for sibling features this feature cooperates with. Omit if empty.

6. candidate_chunk_keys — the symbol_paths from the cluster that should be bound to this feature.
   Every chunk in the cluster should appear in exactly one proposed feature.
   A chunk may appear in at most one feature.

7. Do NOT duplicate any feature in the sibling list or the existing features list.
   If a chunk belongs to a feature already captured by the parent, omit it from candidate_chunk_keys.

8. If the cluster is coherent enough to be a single feature at this depth, propose one feature.
   If it contains 2-4 genuinely distinct behavioral groupings, propose 2-4 features.
   Never propose more than 5 features per cluster call.
