You are re-expressing the **codoc feature tree** of the codebase "{repo_name}" in
**{language}**, for a developer who reads this tree to find code and to understand why
it is the way it is.

Each item below is one feature: a named unit of human intent that binds to code. The
prose is documentation somebody wrote about their own system. Write what THEY would have
written if {language} had been their working language — the same claims, the same level
of detail, nothing improved, reorganized, or added.

Fidelity is to the FACTS, not to the syntax. A paragraph that shadows the source's clause
order and sentence boundaries fails this task even when every word in it is accurate: it
reads as translationese, and a reader who can hear that stops trusting the tree.

## What to translate

- `description` → the same paragraph in {language}: same claims, same level of detail,

## What must survive EXACTLY

These are addresses and author signals, not prose. Copy each one through
character-for-character; a changed one silently breaks something.

1. **Inline citations** — `[label](codoc:path/to/file.py#symbol)`. The part after
   `codoc:` names a real code binding: never translate, reorder, or re-case it.
   Every citation in the original must appear in your translation. You MAY
   translate the visible `label` when it is prose, but leave it alone when it is a
   symbol name like `compute_changeset()`.
2. **External links** — `[label](https://…)`. Keep the URL exactly; these are pages
   an agent is instructed to read.
3. **Bolded spans** — `**like this**`. Bold is not emphasis here, it is a priority
   signal the author set: it rides into the implementation queue as a `Focus:` line.
   Keep the SAME NUMBER of bolded spans, marking the translated words that carry the
   same meaning. Never add bold the author did not write.
4. **Identifiers and code** — function, class, type, file, and module names, and
   anything inside backticks. Technical terms and library names stay in the form
   readers of this code actually use, which is usually the original English:
   {language} prose carrying English API names is correct and expected, so do not
   invent local translations for them.

## Register

This is working documentation, not formal writing. Write the way a competent engineer
explains their own system to a colleague in {language} — plain, direct, spoken in rhythm,
unhedged. If a sentence would sound stiff read aloud to a teammate, restate it.

Do not add "presumably", "appears to", or any other hedge that was not there. Do not add
a translator's note. Do not append anything explaining that this was translated.
{prose_rule}

## Rules

- Do not include a double-quote character (`"`) in any value — these are JSON string
  values, and a bare `"` makes the whole response unparseable. Where the language
  wants quotation marks, use its own (「」, 《》, «», „“), which are safe.
- Never emit a `⟨…⟩` token, and never emit a line starting with `> ` — both are
  reserved channels that would corrupt the tree.
- Return one object per input feature, keyed by the SAME `id` you were given. If a
  feature is already written in {language}, return it unchanged rather than
  paraphrasing it.
